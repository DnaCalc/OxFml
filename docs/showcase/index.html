The executive mental model

OxFml owns formula meaning up to the function boundary. It parses and binds Excel-like formula text, prepares semantic/evaluation artifacts, executes a single formula instance, and publishes deterministic outcomes through the FEC/F3E seam.

Boundary rule: OxFml owns grammar, references, helper forms, host-facing evaluator contracts, trace/replay, and publication. OxFunc owns function/operator semantics and callable batching surfaces.

Ownership map

What OxFml owns, consumes, and exposes

Owns

  • Formula source, channels, parse fidelity, syntax diagnostics.
  • Green/red syntax artifacts and incremental reuse evidence.
  • Name/reference binding and normalized reference ADTs.
  • Semantic plan derivation from bound formula plus OxFunc metadata.
  • Single-node evaluation context, trace, publication, and FEC/F3E contracts.

Consumes

  • OxFunc function/operator catalog, semantic metadata, function-call targets, and callable invocation APIs.
  • Host/coordinator workbook facts: cells, tables, names, snapshots, caller anchors, host query providers.
  • Runtime context: locale profile, date system, time/random seeds, RTD and registered external providers.

Exposes

  • Bound formula artifacts and dependency seeds.
  • Semantic plans and scheduler contracts.
  • Evaluation outputs and returned value surfaces.
  • Commit bundles, typed rejects, replay traces, publication surfaces.

Design pattern

Most layers expose immutable artifacts with stable identity/fingerprint fields. Mutable state exists primarily inside host caches or one evaluation frame, where it is explainable as optimization state rather than semantic truth.

This supports deterministic replay, artifact reuse, and future distributed coordination.

Why separate layers?

  • Text edits and structure edits invalidate different artifacts.
  • Binding can change without parsing changing.
  • Semantic planning can change when catalog/profile facts change.
  • Evaluation can change when values/providers/time/random seeds change.
  • Publication can change when formatting or host surface requirements change.

The formula token hashes stable id, text version, channel, entered text, and stored text.

Green trees are immutable, parentless, full-fidelity syntax. They retain tokens, trivia, spans, delimiters, recovery diagnostics, explicit `@`, spill `#`, whitespace intersection, and structured-reference syntax so later editing/replay layers can explain exactly what was parsed.

Red views and incremental reuse

Red projection: context over immutable syntax

Red nodes add navigation

pub struct RedNode {
  pub index: usize,
  pub kind: SyntaxKind,
  pub span: TextSpan,
  pub parent: Option<usize>,
  pub children: Vec<usize>,
}

Red projection is disposable and reconstructible. It flattens the green tree into an arena with parent/child indices and formula identity.

Reuse rule

if previous.formula_stable_id == formula_stable_id
   && previous.green_tree_key == green_tree.green_tree_key {
  reuse previous_red_projection
}

When syntax is unchanged, red projection can be reused. When structure changes but source does not, green can remain stable while binding/semantics are recomputed.

Edit text

Formula text version changes. Green may change.

Same tokens

Green key unchanged. Red can be reused.

Move formula

Caller row/col changes. Bind context changes.

Rename table

Structure context changes. Binding changes.

Catalog update

Semantic plan changes without syntax change.

SingleFormulaHost is the integration harness that chains parse, red, bind, semantic plan, evaluation, publication, commit, and replay capture.

Consumer groups

  • runtime: runtime environment and managed session facade.
  • editor: live diagnostics, completion, signature help, function help.
  • replay: projection of retained witness and first-host packets.
  • host: empirical oracle and single-formula capture pipeline.
The facades are not a second formula engine. They package canonical artifacts for different consumers while preserving the same parse/bind/plan/evaluate/commit semantics.

Optimizer floor

W075: what changed in the hot evaluator path

Promoted improvements

  • Resolved `FunctionCallTarget` handles in compiled plan nodes.
  • Parsed number/string literal payloads during compile.
  • Explicit `LET`, `LAMBDA`, `IF`, `IFERROR`, ordinary `ResolvedFunctionCall` nodes.
  • Helper slots and slot-only lambda-free `LET` execution.
  • Narrowed closure capture and shared lambda body/parameter storage.
  • Frame-owned scratch stack and callable recursion/stack guard state.
  • Strict pure/context-free precompute with trace preservation.

Rejected experiments

  • Layered runtime slot overlays: semantics held, Mandelbrot regressed.
  • Captured-helper invariant cache wrappers: timing variance/regression.
  • Precomputed helper-key metadata on `LambdaParam`: regression and variance spike.

The workset kept generic infrastructure and avoided function-specific OxFml shortcuts.

Future orientation

Where future work should attach

Near-term engineering

  • Separate evaluator frame helpers into smaller modules once the shape stabilizes.
  • Keep adding regression tests around slots, capture, trace, and references.
  • Use profiling to justify node-indexed scratch or deeper plan lowering.

Cross-repo seam work

  • Prefer OxFunc metadata/cooperation for semantic optimizations.
  • Keep function/operator behavior out of OxFml except via function targets and metadata.
  • Promote shared seam changes with handoff packets and replay evidence.

Longer-term architecture

  • Workbook-level graph planning belongs above OxFml.
  • Green/red/bind/semantic artifacts should remain replayable.
  • Evaluation can become more VM-like without hiding semantic state.
The durable idea: OxFml is a specification-bearing evaluator layer. Its internal optimizer can get faster, but it should continue to expose explicit artifacts that make formula meaning, execution requirements, and commit consequences inspectable.
